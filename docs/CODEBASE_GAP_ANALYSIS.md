## Reconciled scope understanding

LuminaFPM v1 is a strictly READ-ONLY, multi-vendor Firewall Anomaly Management Platform whose core innovation is cross-vendor policy NORMALIZATION feeding a DETERMINISTIC anomaly engine. v1 supports exactly two vendors: Fortinet FortiGate (FortiOS REST/JSON, Bearer token) and Palo Alto PAN-OS (XML API, API key) — NO Cisco. The binding pipeline is an 8-layer, no-bypass architecture: Acquisition -> Vendor Parsing -> Normalization -> PostgreSQL normalized repository -> Deterministic Anomaly Engine -> Risk Scoring -> API-based CTI Enrichment -> AI/LLM SOC Reporting -> Dashboard/Cytoscape graph. Acquisition is read-only (GET/show/monitor/keygen only; never set/edit/delete/move/commit/enable/disable/push) and MUST run asynchronously via per-job-type Celery workers on Redis, never inside the web request cycle; a click creates a job, a worker executes it, raw artifacts are persisted (with manifest + SHA-256, replayable without re-polling), Postgres is written, and the frontend polls job status through an explicit job state machine. The anomaly engine analyzes the NORMALIZED repository ONLY (ADR-010) — never raw FortiGate JSON or PAN XML — is deterministic and explainable across a 46-category taxonomy (single-rule, pairwise same-device, cross-device, historical/conditional), and every finding carries the fixed contract: anomaly_type, rule_id, related_rule_id, severity, confidence (0.00-1.00), technical_reason, evidence, recommendation, detection_mode (config_only/conditional/simulated/future_enhanced), and analysis_run_id. Findings, risk scores (0-100 stored separately so risk recalculates without rewriting evidence), CTI indicators/observations, LLM reports, and benchmark ground-truth/results are all durable first-class records. The data model is a CORRELATION model: vendor-owned objects/services stay device/vendor-scoped beneath canonical normalized_object/normalized_service joined via mapping tables carrying match_method/confidence/mapping_reason; full-merge is rejected. PostgreSQL is the ONLY authoritative store (no MongoDB); all schema changes go through Alembic (Lumina Schema v4); the critical idempotent re-sync key is UNIQUE(device_id, vdom_vsys, vendor_uuid) with upsert + soft-delete (no hard deletes, preserve anomaly/drift history). CTI is API-based (dark-web/Tor scraping is future/optional, not v1); LLM is a provider abstraction (Gemini/OpenAI/Ollama) that explains but is NEVER the anomaly authority. The graph is LOGICAL policy relationships only — never live traffic/NetFlow/DPI. Security is mandatory: encrypted per-device credentials (decrypted only in worker memory, never to frontend/logs, rotatable), RBAC across roles, restricted CORS, structured logging with credential-usage auditing. Benchmarking is ground-truth-driven (benchmark_case/benchmark_result, ~22 FGT + ~23 PAN rules covering all 46 categories) producing precision/recall/F1 as the acceptance gate. Frontend is React + TypeScript + Cytoscape.js (current code is plain JS/JSX with SVG and a fake login — off-spec).

## Biggest conflicts with the volumes (must remove / refactor)

- Mock anomaly engine that fabricates findings: backend/services/anomaly_engine.py:60-105 uses time.sleep(4) + random.choice over 5 templates and returns rule_id=None (line 91), and backend/tasks/anomaly.py:38 then assigns each fake finding to a random rule. This violates the core product identity (deterministic, explainable, normalized-only, every finding linked to the exact affected rule). It must be deleted, not patched — it also fabricates a conditional 'unused_rule / zero hit-count over 90 days' finding with no telemetry, presenting fake live-traffic evidence.
- Synchronous in-request mock acquisition: POST /api/v1/devices/{id}/sync (backend/api/routes/devices.py:88-103) runs MockFirewallConnector and INSERTs straight into policy_rule inside the FastAPI handler, bypassing async Celery jobs, raw-artifact capture, the parser, normalization, and upsert. This single endpoint violates the no-bypass architecture, the async-acquisition mandate, read-only-from-real-devices, and idempotent re-sync simultaneously. The MockFirewallConnector must be removed from the production path.
- Off-direction dark-web/Tor CTI stack: backend/services/lumina_threat_intel/* and backend/services/robin/* (Tor + clearnet scraping, LLM findings, raw-scrape retention), the tor-proxy in docker-compose.yml:22-28, Tor install in backend/Dockerfile:6-13, and the LTI db_models.py threat_intel_* tables embody the OLD direction. v1 mandates API-based CTI (cti_indicator/cti_observation) as primary; this must be demoted to optional/future, decoupled from the pipeline, and removed from the default stack.
- No normalization layer or correlation data model: there is no normalized_object/normalized_service or *_normalization_mapping, and network_object (models.py:86-101) lacks device_id/vendor_id/vendor_object_id/vendor_uuid ownership. The flat object table forces the rejected full-merge behavior and makes cross-vendor traceability and the entire correlation model impossible — this is the keystone gap everything downstream depends on.
- create_all schema management with no Alembic (main.py / models.py:13-23): blocks delivering Lumina Schema v4 (all the missing normalized/risk/cti/benchmark/report tables and the extended rule_anomaly contract) in a controlled, migratable way.
- Cisco/ASA seed content contradicting v1 vendor scope: backend/seed_data.py defines a Cisco vendor and an ASA device with vendor_type 'asa', directly violating the FortiGate+PAN-only v1 scope and the benchmark dataset definition (~22 FGT + ~23 PAN).
- No security baseline: zero authentication on any route, wildcard CORS with allow_credentials=True (main.py:36-43), plaintext DB password committed in .env, and no encrypted per-device firewall credential store (api_token is an admin token, not a device credential). Contradicts the RBAC, least-privilege, and encrypted-secret mandates.
- rule_anomaly contract is incomplete and relationally loose: models.py:159-177 lacks confidence, technical_reason/evidence, recommendation, detection_mode, status, and analysis_run_id, and related_rule_id is a String not an FK to policy_rule — it cannot satisfy the fixed finding contract, the false-positive lifecycle, or ground-truth benchmark matching.

## Delivery risks / items to confirm with client

- The volumes are referenced but not directly re-read in this analysis pass; several exact field lists, the full 46-category taxonomy semantics, severity/confidence rubrics, and table column sets come from specialist digests. Before build, confirm each Table/ADR citation against Volumes/_extracted to avoid building to a paraphrase.
- Deterministic vendor_uuid derivation is critical to the re-sync key but underspecified: for UUID-less FortiGate rules the derivation formula (device_id+vdom_vsys+vendor_rule_id+rule_name+path) must be pinned exactly, or re-syncs will duplicate or collide. The volumes should state the canonical algorithm.
- Conditional/simulated anomalies (unused rule, hit distribution, drift, age) require telemetry/history the read-only platform does not ingest live. The line between 'simulated/benchmark metadata' and forbidden 'fake live evidence' needs explicit acceptance criteria so detection_mode labeling is unambiguous.
- Benchmark dataset is the acceptance gate but must cover all 46 categories with only ~45 rules across two vendors on the shared lab; whether every category is realistically coverable (some are future_enhanced/CTI-coupled) needs client confirmation of which categories are in-scope for v1 precision/recall acceptance.
- Cross-vendor object/service correlation confidence matrix drives whether two policies are 'equivalent' for cross-device inconsistency detection; thresholds and match_method semantics are subtle and, if wrong, produce false cross-device findings. Needs the exact confidence matrix and tie-break rules from Vol4.
- RBAC role set (Admin/Firewall Engineer/SOC Analyst/Auditor/Viewer) and per-endpoint permission matrix are referenced but the authoritative mapping and the auth mechanism (JWT vs token) should be confirmed before wiring dependencies across all routes.
- Large existing off-spec surface (LTI, Robin, mock connector, frontend in JS/SVG, double-registered routers, Cisco seeds) means significant deletion/refactor; client should confirm nothing in LTI/Robin must be preserved as 'future' before it is removed from the default stack.
- Lab device availability (FortiGate 192.168.55.10 / PAN 192.168.55.20) is assumed for connector and benchmark validation; if the lab is not reachable to the engineering team, real-connector acceptance and ACQ-* tests cannot be completed.
- Migrating from create_all to Alembic against any existing populated database risks drift; a clean baseline-from-scratch vs reconcile-existing decision must be made with the client.

### System Architecture & Foundation

_Volume 2 is the binding architectural blueprint for LuminaFPM, a read-only multi-vendor firewall anomaly management platform. It mandates a strict 8-layer architecture (Acquisition -> Parsing -> Normalization -> Repository -> Analysis -> Risk/CTI -> AI Reporting -> Presentation) where no layer bypasses the one below it, and where the anomaly engine analyzes ONLY normalized policies (ADR-010). The approved stack is FastAPI + Python + SQLAlchemy + PostgreSQL-only + Celery + Redis; React+TypeScript + Cytoscape.js; Docker Compose; API-based CTI; and LLM via a provider abstraction (Gemini/OpenAI/Ollama). It prescribes a concrete backend package layout (api/, core/{config,security,logging}, db/{models,session,migrations}, services/{acquisition,parsing,normalization,anomaly,risk,cti,llm,reporting,graph}, workers/{celery_app,tasks}) and a worker split by job type (worker-acquisition/normalization/analysis/cti/reporting). Acquisition must never run inside the web request cycle: a click creates a job, pushed to Redis, executed by a Celery worker, written to Postgres, with the frontend polling job status. It defines acquisition job states, a deterministic 46-category anomaly framework, a 0-100 risk scale, mandatory anomaly evidence fields, encrypted credential storage with rotation/least-privilege, RBAC, and hard read-only constraints (no push/delete/reorder/commit/enable/disable/modify). It requires a Lumina Schema v4 with many new normalized/risk/benchmark/CTI/report tables and Alembic-style migrations. MongoDB and any older Cisco references must be removed; the graph is logical policy relationships only, never live traffic/NetFlow/DPI._

### Firewall Acquisition Layer (Volume 3)

_Volume 3 defines LuminaFPM's read-only firewall acquisition subsystem: how the platform connects to Fortinet FortiGate (FortiOS REST API, Bearer token) and Palo Alto PAN-OS (XML API, API key) devices, authenticates safely, extracts configuration data, stores raw outputs, and hands them to the parser layer. Acquisition MUST be strictly read-only (only GET/show/monitor/keygen-read operations; no set/edit/delete/move/commit/enable/disable/push) and MUST run asynchronously via Celery workers on a dedicated "acquisition" queue backed by Redis, never blocking FastAPI request handlers. Each vendor is implemented as a separate connector module behind a shared ConnectorInterface, selected by a registry on vendor_type. Per device, the connector must extract policies, address objects, address groups, service objects, service groups, and device metadata (interfaces/zones and schedules recommended), returning a vendor-specific AcquisitionBundle plus RawArtifacts and AcquisitionWarnings. Raw API responses must be persisted (filesystem layout /raw_acquisition/{vendor}/{device_id}/{job_id}/...) with an acquisition_manifest.json and SHA-256 hashes per artifact, so parser replay can run without re-polling the device. Acquisition jobs have an explicit lifecycle (queued/running/success/partial_success/failed/timeout/authentication_failed/authorization_failed/connection_failed/rate_limited/parsing_queued) tracked in a job table with metadata (job_id, device_id, vendor_type, requested_by, timing, connector_version, raw_artifact_ids, normalized error_code/message). Credentials must be encrypted at rest, decrypted only in backend/worker memory, never exposed to the frontend or logs, audit-logged, and rotatable without recreating the device. The layer defines normalized error codes, an idempotent retry policy with exponential backoff, FastAPI endpoints for device/credential/test-connection/poll/job-status/artifacts/replay-parser, and a future (non-v1) extension path for FortiManager and Panorama._

### Normalization Engine (Volume 4)

_Volume 4 defines the Normalization Engine — the binding contract that converts parsed FortiGate (REST/JSON) and Palo Alto PAN-OS (XML) configuration into one canonical, vendor-neutral policy model persisted in PostgreSQL, which is the SOLE authoritative input to the deterministic anomaly engine (raw vendor data must never be analyzed directly). It requires recursive group expansion with cycle detection, canonical ANY_OBJECT (0.0.0.0/0, ::/0) and ANY_SERVICE handling, negation preservation, zone/direction normalization (logical only, not packet flow), normalization_warning recording, normalized content hashing, rule_snapshot versioning with soft deletion, and idempotent upserts keyed on (device_id, vdom_vsys, vendor_uuid). The engine is deterministic, explainable, and must run as a Celery service after parser completion, triggering anomaly analysis only on success. ### Database & Data Model (Schema v4)

_Volume 5 defines the full PostgreSQL data architecture for LuminaFPM v1 as a correlation model that separates vendor-owned operational records from canonical normalized records. PostgreSQL is the ONLY authoritative database for v1; MongoDB is explicitly excluded; normalized JSON may exist only as an interchange format, never as source of truth. The schema builds on a "v3 baseline" (vendor, administrator, firewall_device, policy_rule, network_object, rule_object_mapping, rule_anomaly, threat_intelligence, threat_correlation) and adds the "v4 enhancements": network_object ownership fields (device_id, vendor_id, vendor_object_id, vendor_uuid), normalized_object + object_normalization_mapping, normalized_service + service_normalization_mapping, risk_assessment, anomaly_execution_log, benchmark_case, benchmark_result, cti_indicator, cti_observation, and llm_report. ### Benchmark & Evaluation Framework (Volume 7)

_Volume 7 defines how LuminaFPM proves the anomaly engine works: a controlled, ground-truth-driven evaluation framework rather than visual inspection. It mandates two persistence tables — benchmark_case (the authoritative expected-outcome / ground-truth matrix) and benchmark_result (per-run comparison output). Benchmark cases are split into ATOMIC cases (isolate exactly one expected anomaly, e.g. shadowing-only, redundancy-only, missing-logging-only, unprotected-allow-only, poor-naming-only) and COMPOUND cases (deliberately trigger multiple anomalies on one rule or rule pair to mirror real rulebases, e.g. ANY->DB allow with no profile + logging disabled yielding overly_permissive + any_to_sensitive + unprotected_allow + logging_disabled). A phase-1 benchmark dataset is required: ~22 FortiGate rules + ~23 Palo Alto rules (~45 total) covering the full 46-category anomaly taxonomy, built on the Hybrid Parallel Shared-Network lab with matched objects on both vendors (LAN_NET, DMZ_NET, DB_NET, WEB_SERVER, DB_SERVER, ADMIN_PC, MALICIOUS_IP) and intentionally engineered shadowing/redundancy via rule ordering. A deterministic evaluation runner executes the full pipeline (acquire -> parse -> normalize -> anomaly engine), compares rule_anomaly output against benchmark_case expectations, writes benchmark_result rows, and computes TP/FP/FN, precision, recall, F1, severity-match-rate, and explanation-match-quality. The framework also requires import/export of benchmark matrices, automated benchmark runs after every anomaly-engine change, a frontend Benchmark Center, and preservation of the dataset as regression evidence. Detection modes (config_only, conditional, simulated, future_enhanced) must label runtime/simulated cases; the engine evaluates normalized policies only. Acceptance requires all core config-only atomic anomalies detected, cross-device inconsistency detected, all major compound findings present, simulated cases clearly labeled, and every finding showing affected rule, related rule, and reason. None of this exists in the codebase today._

### Risk Scoring Engine

_Volume 8 specifies a SEPARATE, deterministic Risk Scoring Engine that prioritizes firewall policy findings by transforming anomalies, exposure, security posture, CTI evidence, and asset sensitivity into a single 0-100 actionable score. It is explicitly distinct from anomaly detection: an anomaly explains WHAT is wrong; risk scoring explains WHAT should be fixed first. The engine sits downstream of the Anomaly Engine (rule_anomaly), the CTI Engine (cti_observation), Inventory (device/firmware context), and Objects (asset sensitivity), and produces risk_assessment records plus a dashboard priority queue. The score is the capped sum of eight additive factor sub-scores: anomaly_score + exposure_score + asset_sensitivity_score + security_posture_score + logging_score + cross_vendor_score + cti_score + lifecycle_score, with min(100, ...). Scores map to five tiers: 0 Informational, 1-39 Low, 40-69 Medium, 70-89 High, 90-100 Critical. Each factor has a recommended weight range, and the FULL factor breakdown MUST be stored (JSONB) per assessment so SOC engineers understand why a rule is high risk. The engine scores at three scopes (rule, device, object); device risk is a weighted average of top-N rule risks plus firmware/stale-poll/critical-anomaly modifiers and must not hide individual rule evidence. CTI contributes to risk (not as an anomaly by default), cross-vendor inconsistencies between FortiGate and Palo Alto raise risk and must carry both involved rules in the evidence payload, scoring weights must be versioned (calculation_version), and recalculation is triggered by parser sync, anomaly runs, new CTI observations, asset-sensitivity changes, and suppression/accepted-risk (which preserves original score history). Risk APIs and history must feed the dashboard and SOC reports; unit tests for expected score bands are required._

### Threat Intelligence (CTI) Engine

_Volume 9 defines a READ-ONLY, API-based CTI enrichment engine that sits ALONGSIDE (never inside) the deterministic policy-anomaly engine. Its pipeline is: take normalized policies + device inventory -> extract PUBLIC indicators (IPs/CIDRs/FQDNs/URLs from normalized_objects, plus vendor+firmware_version context from firewall_device) -> generate analyst-friendly search phrases via LLM (the LLM never decides a threat is real without provider evidence) -> query authorized CTI providers through a uniform CTIProvider abstraction (AbuseIPDB, OTX, VirusTotal, a vendor-advisory provider, and NVD/CVE) -> normalize each provider response into a cti_observation tied to a cti_indicator -> correlate indicators to rules (IOC value appears in rule sources/destinations) and devices (firmware matches a CVE/advisory target version) -> feed correlations into risk_assessment (CTI is a risk contributor, NOT an automatic policy anomaly; a "threat exposure anomaly" is created only when a policy directly permits a high-confidence malicious indicator). The volume is explicit that v1 is legal API-based CTI as the PRIMARY (and only required) implementation; uncontrolled dark-web/illicit-marketplace scraping is OUT of v1 scope. It mandates: never send RFC1918/private IPs or confidential hostnames to external providers unless explicitly configured; rate-limit and back off on 429; cache with TTL; retry transient failures with exponential backoff; record partial_success rather than failing the whole run; and full traceability of every observation to a provider + lookup time (raw_response_hash, observed_at, last_seen). The Threat Center UI and SOC report must show indicators, providers, confidence, affected rules, and risk impact, and must separate confirmed provider evidence from LLM-generated explanation._

### AI / LLM Architecture (Volume 10)

_Volume 10 defines the AI/LLM architecture as a strictly bounded productivity aid that never holds authority over anomaly truth. AI's six responsibilities are: generate CTI search queries from device/firmware/inventory context; summarize CTI provider results into SOC language; generate technical reports for risky rules/devices; explain anomaly evidence in human language; produce executive summaries from deterministic findings; and recommend manual review actions. AI must NOT decide anomaly truth, push firewall changes, replace CTI evidence, invent CVEs/threat claims, classify private data without policy, or hide uncertainty. A provider abstraction (LLMProvider) with exactly four methods — generate_cti_queries, summarize_cti_findings, generate_soc_report, generate_executive_summary — must be implemented for three configurable adapters: GeminiProvider (cost-effective v1 default), OpenAIProvider (high-quality reasoning), and OllamaProvider (privacy-focused local). Four workflows map specific evidence inputs to outputs (CTI Query Gen, CTI Review, Rule Report, Executive Summary), and the SOC report has a fixed seven-section structure. Every report must be evidence-grounded: reference DB evidence IDs, label CTI-sourced vs generated-analysis claims, carry timestamp + model/provider metadata, and be persisted in an llm_report table with prompt version and evidence references after passing evidence-grounding validation. Failure handling is mandatory: LLM outages must NOT fail acquisition or anomaly analysis — the platform still shows deterministic anomalies/risk; failed AI jobs are logged; partial-CTI reports are labeled partial; provider errors show user-friendly messages. Security controls require encrypted API keys never sent to frontend, CTI text treated as untrusted/delimited (prompt-injection defense), redaction/local-Ollama option for sensitive policy data, and evidence-backed + confidence-labeled output to curb hallucination._

### Security Architecture

_Volume 12 defines LuminaFPM as a sensitive security-management system that stores firewall inventory, policies, credentials, anomalies, and AI reports, and therefore mandates a full security model across nine domains. (1) Read-only enforcement is the cornerstone: connectors must call read-only firewall APIs only — no commit/set/edit on PAN-OS, no config-write endpoints on FortiGate, firewall accounts must hold minimum read permissions, code review must reject any write-capable firewall operation in v1, and the UI must not include remediation/push buttons. (2) Authentication must use a secure session or JWT model with expiration, modern password hashing for any local accounts, session inactivity timeout, separate service accounts from human users, and MFA recommended for production. (3) Authorization is a five-role RBAC model (Platform Admin, Firewall Engineer, SOC Analyst, Auditor, Viewer) enforced by RBAC middleware. (4) Secrets must never live in source code, must be encrypted at rest, must never be returned to the frontend, must support rotation, and secret-usage must be logged without logging the value, with distinct lab/staging/prod credentials. (5) API security requires Pydantic input validation, SQLAlchemy parameterized queries, restricted CORS origins, rate limiting on login and expensive job-creation endpoints, authorization on every export, and error messages that never leak secrets or stack traces. (6) Data protection treats rules/object-names/management-IPs/reports as sensitive, encrypts backups, redacts secrets from logs, allows suppression of internal indicators sent to external CTI/LLM, and defines retention policies. (7) Audit logging must record a fixed set of critical events. (8) Database hardening requires least-privilege DB users, migration-runner-only schema changes, encrypted/access-controlled backups, audit tables protected from casual deletion, and PII minimization. (9) Deployment hardening forbids public exposure of PostgreSQL/Redis, mandates env-var/secret-manager config, least-privilege containers, CI dependency scanning, HTTPS in production, and centralized access-controlled logs; plus defined incident/failure behaviors for firewall-auth, CTI-down, LLM-down, DB-unavailable, and suspicious activity._

### Deployment & Operations (Volume 13)

_Volume 13 defines how LuminaFPM v1 is deployed and operated as a production-like Docker Compose stack (Kubernetes is explicitly future work). The volume contains no Tor/dark-web infrastructure; CTI in v1 is outbound API-based from workers._
